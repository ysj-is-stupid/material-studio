# 素材制作网站验收场景

本清单对应题目 R-01 至 R-14，记录自动化检查、容器实跑和未验证项。下方保留了先前的环境故障记录；最终结论以文末“最终验收结果”为准。

## 已通过的自动化检查

1. 前端 Node 22：`npm run lint`、`npm run typecheck`、`npm run test`、`npm run build` 均通过。11 项前端测试覆盖多任务与查询异常、轮询生命周期、身份入口、上传替换与移除、迟到响应隔离、离页取消、空列表及错误模板反馈。
2. 后端 Java 21：`mvn -B verify` 通过。9 项测试覆盖后台三个阶段顺序、三个指定阶段失败后不执行后续阶段、两张上传图合成可读 PNG、伪装成 PNG 的无效文件被拒绝、A/B 身份切换与基础健康接口。
3. `docker compose config --quiet` 通过，说明 Compose 文件可解析；这不证明镜像可构建或服务可连接。

## 阶段 7 必须实跑的场景

1. **启动与初始化（R-01、R-02、R-12～R-14）**：在容器环境执行 `docker compose up --build -d`；检查三服务运行、前端首页、经前端代理的 `/api/health`、三条种子模板和封面。确认使用项目自带素材，无付费服务。
2. **模板与上传（R-02、R-03、R-11）**：切换“全部 / 旅行纪念 / 宠物日常”；进入一图与两图模板；验证选图、预览、替换、移除、上传中、上传失败；拒绝错误类型、超限大小、空文件和不存在模板；在小屏及键盘操作下检查页面可用。
3. **成功任务（R-04、R-05、R-07、R-09）**：上传项目示例 PNG 后提交；检查接口先返回 202 与任务 ID；数据库依次记录 `ASSET_CHECK → GENERATE → FINALIZE`；任务最终成功并显示可预览 PNG。多次 GET 只读状态，不改变阶段。
4. **指定失败和耗时（R-05、R-06、R-07）**：分别在三个阶段注入失败；确认失败阶段和可读原因入库，后续阶段没有开始；调整每阶段延迟到 3 秒，能观察排队与处理中状态。
5. **多任务与刷新（R-08、R-09）**：连续提交至少两个任务，一个成功、一个失败；检查状态、阶段、错误和结果互不串扰；刷新历史页后从 Java 恢复记录并继续跟踪未完成任务；终态停止轮询，没有活动任务时没有定时查询。
6. **身份与异常（R-03、R-07、R-10）**：在页面右上角切换演示用户 A→B→A，检查 B 看不到 A 的任务，切回 A 后原记录恢复；用普通与无痕浏览器再检查浏览器间的隔离；暂时阻断状态查询但不停止后端，检查前端保留旧状态并显示查询错误，恢复网络后继续读取；分别检查模板空数据、加载失败和上传请求失败的反馈。
7. **交付复核（R-12～R-14）**：检查源码、依赖锁文件、SQL、CI、配置示例和 README；在容器内执行前后端 CI 命令；核对已完成、未完成与回滚说明。

## 最终验收结果（2026 年 11 月 8 日）

之后 Docker Hub 成功提供 MySQL 8.4 镜像；Node 22、Maven 3.9 / Java 21 和 Temurin 21 镜像经可访问的镜像站下载并在本机标为对应官方镜像名。项目 Dockerfile 和 Compose 保持标准镜像引用。后端容器构建改用 Maven Central 镜像及依赖缓存，最终在容器内完成 `mvn verify`；前端容器构建执行 lint、类型检查、测试和生产构建。标准命令 `docker compose up --build -d` 退出码 0，前端、Java 和 MySQL 三项服务运行，MySQL 健康检查通过。

实际接口与浏览器验收：

1. `/api/health` 经 Next.js → Java → MyBatis → MySQL 返回 `{"database":"UP","status":"UP"}`；`/api/templates` 返回三条模板、两种分类和不同上传数量。首次导入曾因 MySQL 客户端默认 latin1 造成中文乱码，已在 `02-seed.sql` 加 `SET NAMES utf8mb4`，并用全新临时 MySQL 容器验证初始化后中文标题正确。
2. `tests/smoke_live.py` 通过前端公共地址实际上传两张 PNG、提交成功任务和三个分别在 `ASSET_CHECK`、`GENERATE`、`FINALIZE` 失败的任务。成功任务依次经过三个服务端阶段，结果 PNG 可读取；失败任务在指定阶段停止且不产生后续阶段。连续提交的任务有独立状态，终态不会因后续查询倒退。
3. 两个匿名身份的任务和素材访问隔离；错误图片数量被服务端拒绝；历史接口返回本人任务。浏览器实际完成选图、上传、提交、看到成功结果、刷新详情与进入历史页，记录和结果均可恢复。
4. 桌面、390 像素小屏页面已截图检查；小屏文档宽度与视口同为 390 像素，没有横向溢出。查询异常与后台失败区分、活动任务轮询和终态停止轮询由前端自动化测试验证。
5. R-10 补验：新增页面右上角“演示账户”入口和 A/B 切换。重新构建前后端镜像并启动三服务后，`tests/smoke_live.py` 经 `localhost:3000` 验证 A 有四项任务、B 初始历史为空且无法读取 A 的任务、切回 A 后四项记录恢复。后端身份切换单元测试 2 项和前端入口测试 1 项通过。页面切换请按 README 的 R-10 小节手动确认。

当时仍未验证：GitHub Actions 在远端平台的实际运行（彼时目录不是 Git 仓库）；生产环境部署。题目不要求公网部署或在线 CI 截图。本次本地容器运行可以证明题目要求的核心业务闭环。后续 GitHub 仓库与 Actions 补验结果见文末。

## R-03、R-06、R-08 自动化补验（2026 年 11 月 8 日）

1. 前端新增 7 项测试，合计 11 项通过：替换上传时旧请求中止且迟到结果不覆盖新素材；移除清空就绪状态；非法类型在客户端阻止上传；上传失败显示错误；列表加载失败后重试及空列表提示；不存在模板提示；混合完成与运行中任务的轮询停止、离页请求取消及旧身份迟到响应隔离。容器构建执行 lint、类型检查、测试和 Next.js 生产构建，最终全部通过。构建期间曾有两次容器进程 `SIGSEGV`，随后不改源码重试通过；该偶发现象需在新的验收环境留意。

## R-03、R-11 浏览器可用性补验（2026 年 11 月 8 日）

1. 使用独立的 Chrome 浏览器会话访问运行中的 Compose 服务，检查首页、旅行明信片详情和历史页在 320、360、390、768、1440 像素视口的文档宽度和账户入口位置；均无横向溢出，账户入口位于可见区域。核对桌面、小屏首页、详情、历史及账户面板截图。320 像素时最初导航文字被挤压换行，已调整为两行导航并复查截图。
2. 使用浏览器原生文件输入协议实际选择项目自带的两张 PNG：第一张上传就绪后替换，预览地址随之变化；移除后回到空状态；重新上传两张后提交，页面出现任务已受理提示。通过页面导航进入历史，刷新后仍显示该任务；点击账户 A→B 时 B 历史为空，切回 A 后原任务恢复。
3. 用 Tab 遍历制作页，发现视觉隐藏的文件输入原本也会获得焦点；现已将该输入移出 Tab 顺序。复测确认可见的“选择图片”按钮与账户按钮有 3 像素焦点轮廓，按 Enter 能分别触发文件输入和打开账户面板。容器内前端 11 项测试、lint、类型检查和生产构建通过，并已重新部署前端容器。
